몰려오는 요청을 서버가 얼마나 빨리 받을지(rate limit)와 동시에 몇 개 처리할지(concurrency)를 제어하는 시스템입니다. 실제 백엔드 서버(Stripe API, HTTP 커넥션 풀, DB pool 등)의 축소판.

요청이 거치는 5단계

  1. 요청 도착 — 버튼 눌러 POST /api/work 발사.
  2. 토큰 — 입장권 1장 필요. 초당 5장 리필, 최대 10장.
  3. 토큰 대기(rate-q) — 토큰이 없으면 여기서 대기. 5초 초과 시 429.
  4. 큐(queue) — 토큰은 받았지만 슬롯이 꽉 차면 여기서 대기. 꽉 차면 503.
  5. 처리(slot) — 실제 작업 수행. 동시 최대 3개. 500~2000ms 랜덤.

로그 읽는 법

10:23:45  #7  200  1240ms  work=823ms

  • #7 — 7번째 요청(burst 내 순번)
  • 200 — HTTP 상태. 200=완료, 429=rate timeout, 503=queue full
  • 1240ms — 요청 발사부터 응답까지 전체 시간
  • work=823ms — 실제 처리 시간. 1240 − 823 = 417ms가 대기 시간

10:23:48  #34  429  Too Many Requests (rate timeout)

→ 빨간 줄. 토큰 대기 5초 초과해서 거절됨.

burst done  25300ms  200:65 429:35 503:0

→ 100건 중 65건 성공, 35건 429 거절, 503 없음.

이렇게 해보세요

  1. send 1~2번 — 여유 상태 관찰. 슬롯 1/3 깜빡, 토큰 10에서 잠깐 감소 후 리필.
  2. burst 10 — 동시성 제한 관찰. 슬롯 3/3 포화, 큐 7개 쌓임.
  3. burst 30 — shaping 관찰. 토큰 0, rate-q 20개 쌓였다가 서서히 드레인. 전부 200.
  4. burst 100 — 거절 발생. 약 30~40% 429로 떨어짐. 배너 🔴 saturated.
  5. burst 200 — 극한. rate-q까지 overflow해서 503도 섞임.
  6. reset — 카운터 초기화. 활성 요청은 안 끊김.

어느 카드가 빨개지나로 원인 파악

  • token 0/10 → 토큰이 소진됨. 자연스러운 현상.
  • rate-q 숫자 큼 → 토큰 리필보다 유입이 빠름. 429 발생 임박.
  • queue 숫자 큼 → 처리 속도가 유입보다 느림. 503 발생 임박.
  • slots 3/3 지속 → 최대치 사용 중. 정상 full-throughput.
